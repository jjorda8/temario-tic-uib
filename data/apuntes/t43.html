1. Arquitectura cliente/servidor

  • El cliente solicita servicios y el servidor los presta, comunicándose por red mediante un protocolo. Separa presentación, lógica y datos para repartir la carga y centralizar recursos.
  • Cliente pesado (fat client: lógica en el cliente, aplicación de escritorio) frente a cliente ligero (thin client: solo presentación, por ejemplo el navegador).
  • Middleware: software intermedio que facilita la comunicación entre componentes (RPC, colas de mensajes, ORB/CORBA, servidores de aplicaciones).
  • Ventajas: centralización, escalabilidad, mantenimiento y seguridad. Inconvenientes: dependencia del servidor y de la red, congestión.

  • Las capas lógicas (layers) pueden desplegarse en niveles físicos (tiers) distintos.
  • Ventajas: cada capa se escala, se protege (por ejemplo, la base de datos no es accesible desde Internet) y se mantiene por separado.
  • Servidores de aplicaciones: Jakarta EE (WildFly, Payara, WebLogic), contenedores de servlets (Tomcat), .NET (IIS/Kestrel), Node.js.
  • Operación típica: el cliente envía una petición HTTP → servidor web o balanceador → servidor de aplicaciones (lógica, sesiones, transacciones) → base de datos → respuesta (HTML o JSON).

3. Arquitecturas de servicios web

  • Servicio web: componente que ofrece funcionalidad a otras aplicaciones a través de la red mediante protocolos estándar, independientemente de la plataforma.
  • SOA (arquitectura orientada a servicios): la aplicación se construye a partir de servicios reutilizables y débilmente acoplados; a menudo con un ESB (bus de servicios) que enruta y transforma mensajes. Evolución hacia los microservicios.
SOAP
  • Protocolo basado en XML (W3C): mensaje con Envelope, Header opcional, Body y Fault para errores. Normalmente sobre HTTP, pero independiente del transporte.
  • Contrato formal en WSDL (operaciones, mensajes, tipos con XSD, enlace y punto de acceso). UDDI como registro (en desuso).
  • Estándares WS-*: WS-Security (firma y cifrado de mensajes), WS-ReliableMessaging, WS-Addressing.
  • Muy usado en la Administración para la interoperabilidad entre organismos (servicios de intermediación de datos, plataforma SCSP).
REST
  • Estilo de arquitectura definido por Roy Fielding (2000). Se basa en recursos identificados por URI y manipulados con los métodos HTTP.
  • Restricciones: cliente-servidor, sin estado, cacheable, interfaz uniforme, sistema en capas, código bajo demanda (opcional). HATEOAS: las respuestas incluyen enlaces a las acciones posibles.
  • Métodos: GET (leer; seguro e idempotente), POST (crear; no idempotente), PUT (sustituir; idempotente), PATCH (modificar parcialmente), DELETE (borrar; idempotente).
  • Códigos de estado: 2xx éxito (200 OK, 201 Created, 204 No Content), 3xx redirección (301, 304), 4xx error del cliente (400, 401 sin autenticar, 403 prohibido, 404, 409), 5xx error del servidor (500, 503).
  • Formatos: normalmente JSON; documentación con OpenAPI (antes Swagger).
Otros protocolos
  • GraphQL: el cliente pide exactamente los campos que necesita en una única petición.
  • gRPC: llamadas remotas con Protocol Buffers sobre HTTP/2, muy eficiente entre microservicios.
  • Mensajería asíncrona: AMQP (RabbitMQ), Kafka, MQTT (IoT); WebSocket para comunicación bidireccional.
  • Seguridad: HTTPS/TLS, OAuth 2.0 y tokens JWT, claves de API, WS-Security, limitación de peticiones (rate limiting), gateways de API.
  • Protocolos de base: HTTP/1.1, HTTP/2 (multiplexación, binario) y HTTP/3 (sobre QUIC/UDP).

Claves para el test

  • Tres capas: presentación, negocio y datos.
  • SOAP = XML + WSDL; REST = recursos + métodos HTTP, sin estado.
  • GET, PUT y DELETE son idempotentes; POST no.
  • 401 = no autenticado; 403 = sin permiso; 201 = creado.
